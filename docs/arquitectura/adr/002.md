# ADR 002: Selección de Kong como API Gateway

- **Estado:** Aprobado
- **Fecha:** 2026-09-21
- **Autores:** Equipo de Arquitectura

## Contexto

Como parte de la migración del monolito hacia una arquitectura de microservicios mediante el patrón Strangler Fig, se requiere un punto de entrada centralizado para las solicitudes de los clientes.

Este componente debe permitir enrutar las peticiones a los servicios correspondientes, aplicar políticas de acceso y facilitar la incorporación gradual de nuevos servicios sin exponer directamente toda la infraestructura interna.

## Alternativas consideradas

### Opción 1: Kong Gateway

Utilizar Kong como API Gateway para administrar el enrutamiento y aplicar políticas mediante plugins y configuración centralizada.

**Ventajas:**
- Enrutamiento de solicitudes hacia diferentes servicios.
- Posibilidad de incorporar autenticación, limitación de solicitudes y otras políticas mediante plugins.
- Facilita la incorporación gradual de microservicios durante la migración.

**Desventajas:**
- Requiere configuración, operación, monitoreo y mantenimiento.
- Algunas funcionalidades avanzadas pueden depender de la edición y los plugins utilizados.

### Opción 2: NGINX como proxy inverso

Utilizar NGINX para enrutar las solicitudes hacia los servicios backend.

**Ventajas:**
- Es una alternativa flexible y ampliamente utilizada para proxy inverso y balanceo de tráfico.
- Puede cubrir necesidades de enrutamiento con una configuración relativamente sencilla.

**Desventajas:**
- La implementación de políticas específicas de API puede requerir configuración adicional o componentes complementarios.

### Opción 3: Enrutamiento dentro de cada servicio

Permitir que los clientes accedan directamente a los servicios o que cada componente gestione su propio enrutamiento.

**Ventajas:**
- Reduce la necesidad inicial de incorporar un gateway dedicado.

**Desventajas:**
- Distribuye las responsabilidades de acceso y enrutamiento.
- Aumenta la complejidad cuando crece el número de servicios.
- Dificulta mantener políticas uniformes en un punto central.

## Decisión

Se selecciona **Kong Gateway** como API Gateway objetivo para la arquitectura de microservicios.

Kong actuará como punto de entrada para las solicitudes de los clientes y permitirá:

- Enrutar las peticiones a los servicios backend correspondientes.
- Centralizar las políticas de acceso que se configuren.
- Incorporar mecanismos de autenticación, limitación de solicitudes y observabilidad cuando sean necesarios.
- Facilitar la migración incremental mediante el patrón Strangler Fig, redirigiendo el tráfico a los servicios nuevos conforme estén disponibles.

La selección se basa en la necesidad de centralizar el enrutamiento y las políticas de API. La adopción definitiva deberá considerar los requisitos de infraestructura, seguridad, operación y licenciamiento del proyecto.

## Consecuencias

### Positivas

- Punto de entrada centralizado para los servicios.
- Mayor uniformidad en la aplicación de políticas de API.
- Flexibilidad para incorporar nuevos servicios durante la migración.
- Posibilidad de aplicar controles de tráfico y seguridad según los requisitos.

### Desafíos y riesgos

- El gateway se convierte en un componente crítico que requiere alta disponibilidad y monitoreo.
- Una configuración incorrecta puede interrumpir el acceso a varios servicios.
- Deben gestionarse adecuadamente los certificados, las credenciales y las políticas de seguridad.
- Se requiere definir responsabilidades de operación, actualización y mantenimiento.
- La selección y configuración de plugins debe considerar compatibilidad, costo y necesidades reales.

## Consideraciones de implementación

- Definir rutas explícitas hacia los servicios backend.
- Evitar exponer directamente servicios internos que deban permanecer privados.
- Configurar autenticación y autorización según los requisitos de cada API.
- Establecer límites de solicitudes y tiempos de espera apropiados.
- Monitorizar disponibilidad, errores y latencia.
- Evaluar redundancia y alta disponibilidad para evitar un punto único de falla.
